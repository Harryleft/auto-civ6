## A. 仓库代码缺陷：上次报 1 处，实际 4 处

上次只报了 `FEATURE_OVERLAY_COLORS`。这次把 `terrain-colors.ts` 里**三张表**全部重新核对了游戏数据库。

### A1. `FEATURE_OVERLAY_COLORS` 映射错误（上次已报，证据不变）

仓库写 `0=FOREST, 1=JUNGLE, 2=MARSH, 3=OASIS`；

### A2. `ROAD_COLORS` 标签错位 + 缺索引 3（**新增**）

### A3. `DIPLO_STATE_NAMES` 整体错位一位（**新增，影响最直接**）

仓库**自己**的 Python/Lua 侧就写着权威列表（`src/civ_mcp/lua/diplomacy.py:35`）：

```lua
local states = {"ALLIED","DECLARED_FRIEND","FRIENDLY","NEUTRAL","UNFRIENDLY","DENOUNCED","WAR"}
--               0          1            2         3          4           5          6
```

另有旁证 `diplomacy.py:1006-1008`：`stateIdx == 0` → 已结盟；`stateIdx == 1` → 须先宣布友谊。

而网页端（`web/src/lib/diary-types.ts:17`）是：

```ts

  0: "Allied", 1: "Friendly", 2: "Neutral", 3: "Unfriendly",
  4: "Denounced", 5: "Hostile", 6: "War",

```

**漏了索引 1 的 `DECLARED_FRIEND`，导致索引 2 之后整体前移一位**：

| 实际状态 | 网页显示 |
|---|---|
| 2 = FRIENDLY | ❌ "Neutral" |
| 3 = NEUTRAL | ❌ "Unfriendly" |
| 4 = UNFRIENDLY | ❌ "Denounced" |
| 5 = DENOUNCED | ❌ "Hostile"（`Hostile` 根本不是合法状态） |
| 6 = WAR | ✓ 碰巧对上 |

使用点：`web/src/components/diplomacy-panel.tsx:62`。**外交面板会把友好显示成中立、把谴责显示成敌对。**

### A4. 文档与代码不一致：MCP 存档保留数量（**新增，次要**）

- `docs/agent-recovery.md:5`：「保留最新 **5** 个」
- `src/civ_mcp/end_turn.py:1601`：`cleanup_old_autosaves(keep=8)`
- `src/civ_mcp/game_lifecycle.py:396`：函数签名默认 `keep: int = 5`

实际磁盘上剩 **9** 个（`0_MCP_0167`–`0175`）。三处说法互不一致。

### A 组已核对**无误**的部分

| 表 | 结论 |
|---|---|
| `TERRAIN_COLORS` 0–16 | ✅ 与游戏 `Terrains.xml` 逐项一致 |
| `RESOURCE_META` / `LUXURY_META` | ✅ 按**名字**索引（`HORSES`/`IRON`），不受 ID 顺序影响 |
| `DIFFICULTY_META` | ✅ 字符串键；只覆盖 3 个难度属设计取舍（有 `?? 99` 兜底） |

### A 组根因归纳

**这些表的作者默认「ID 顺序 = 直观顺序」，但游戏数据库的 ID 会因为资料片/DLC 的加载顺序而整体偏移。凡是手写数字键的表都不可靠。**

建议：把 ID→名称的权威表**从游戏数据库导出**（`GameInfo.Features` / `Routes` / `Terrains`），或至少在 CI 里加一个「用真实快照校验 ID 表」的测试。仓库已经有 `map/` 快照，做这件事成本很低。

## B. 游戏设置：上次改 3 项，漏了 4 项检查

### 上次改的 3 项

| 项 | 状态 |
|---|---|
| `EnableTuner 0→1` | ✅ 生效，必要 |
| `PlayIntroVideo 1→0` | ✅ 生效，解决了"卡在动画界面" |
| `MaxJobThreads -1→4` | ❌ **被游戏覆盖回 `-1`，从未生效** |

### B1. `MaxJobThreads` 没有持久化机制（**最实质的遗漏**）

游戏启动时会重写 `AppOptions.txt`，所以手改一次没用。仓库的正确做法是 `game_launcher._ensure_job_thread_cap()`——**每次拉起游戏前幂等重写**（并做首份备份）。

我在 `supervise.py` 里没做这一步，所以第 175 回合的引擎崩溃**是在缓解措施缺席的情况下发生的**。

### B2. `AutoEndTurn` 上次没验证（**已补验**）

README 要求「Auto End Turn = Disabled」——它在 `UserOptions.txt`，不在 `AppOptions.txt`（我上次只看了后者）。

实机值：`AutoEndTurn 0` ✅ **本来就对**，无需改动。

### B3. 与「失焦暂停」相关的项，上次完全没查（**新增**）

`AppOptions.txt [Performance]`：

```
InactiveTickIntervalInMS 32      ; 非活动时每 32ms 一跳（可设 0 = 持续 tick）
ThrottleWhileInactive 0          ; 不因非前台而降频
TickIntervalInMS 0               ; 前台持续 tick
```

`ThrottleWhileInactive` 已经是 0（不降频），但实机仍是「失焦 → 游戏核心不执行 Lua」。所以 Civ VI 的暂停是**另一套机制**（单机在前台丢失时挂起游戏核心），这三个 tick 参数**不是**开关。

**但 `InactiveTickIntervalInMS 0` 是一个未验证的候选缓解措施**——如果失焦时的 32ms 跳变导致 tuner 队列迟迟不被抽干，设成 0 可能改善。本次没测。

### B4. 另外两项配置事实（**新增**）

| 项 | 值 | 含义 |
|---|---|---|
| `FullScreen` | `2` | 无边框窗口化。README 建议"窗口化"；`0` 是真窗口化，可能走不同的焦点路径。未验证 |
| `ClipCursor` | `1` | 光标被锁在游戏窗口内，会影响程序化点击的边界行为 |
| `AutoProdQueue` | `1` | **自动排产开启**——这解释了为什么有时会弹「选择生产项目」、有时不会 |
| `AutoSaveKeepCount` | `10` | 游戏自带自动存档保留数（与 MCP 的 `0_MCP_*` 是两套） |

## C. 我写的三个脚本：上次未审，本次发现 9 个问题

### 严重（直接导致对局失败）

**C1. 排产表里没有开拓者 —— 全程 1 座城的直接原因**

```python
# play.py:63  PROD_PRIORITY
"DISTRICT_CAMPUS", "DISTRICT_COMMERCIAL_HUB", "DISTRICT_HARBOR",
"DISTRICT_THEATER", "DISTRICT_HOLY_SITE", "DISTRICT_ENCAMPMENT",
"BUILDING_MONUMENT", "BUILDING_GRANARY", "BUILDING_WATER_MILL",
"BUILDING_WALLS", "UNIT_BUILDER", "UNIT_TRADER",
"UNIT_ARCHER", "UNIT_SPEARMAN", "UNIT_WARRIOR",
# ← 没有 UNIT_SETTLER
```

`WAR_PRIORITY` 同样没有。执政官在代码层面**不可能造开拓者**，所以从回合 105 到 175 一直是 1 座城。这不是策略不好，是**功能缺失**。

**C2. 没有处理「选择生产项目」弹窗**

`grep 'SETTLER|选择生产|city_action' play.py` → 空。城市造完东西没排产时游戏会弹这个，而它阻塞游戏核心 → 连第一个 `get_game_overview` 都挂住。这正是那次 20 分钟卡死的场景。

### 中等（拖慢恢复 / 丢失缓解措施）

**C3. `end_turn` 超时设成 1200 秒**
`play.py:302`。卡一次要白等 20 分钟才触发总控恢复。应当 ≤180 秒。

**C4. `recover()` 无条件杀掉游戏**
只要 play.py 非零退出就杀游戏重启，哪怕游戏本身好好的、只是 MCP 挂了。每次多花 60–90 秒。应先探测 `4318` + GameCore/InGame 是否还在。

**C5. `recover()` 不重新固定 `MaxJobThreads`**
即 B1。恢复流程本身就是最该做这件事的地方。

### 轻微

**C6. `send.py` 读的是已改名的字段**
我把 daemon 的 `focused` 改成了 `focus_failures`，但 `send.py:87` 还在 `rec.get('focused')` → 显示永远是 `None`。

**C7. `_play.log` 每条日志整文件重写**（`log()` 里 `write_text` 全量），O(n²) I/O。

**C8. `mcp_daemon.py` 每 0.4 秒 `CMD.read_text()` 读整个文件**，文件随回合增长。

**C9. `AT_WAR` 在生产决策之后才更新**
`play.py` 先做城市排产、后查外交，所以排产用的是**上一回合**的战争状态，被突袭时会晚一回合转入防守。
