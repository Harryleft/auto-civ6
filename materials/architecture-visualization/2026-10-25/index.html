01
System Panorama

系统全景：CLI 是唯一操作面，MCP 是内部实现

一次操作的真实链路是：Agent 宿主 → civ6 CLI（唯一操作面）→ 内部 stdio MCP → 运行层 → FireTuner → 游戏引擎，再把回读事实送回模型。客户端不注册 civ6 MCP，也不直连内部服务；运行层仍是唯一持有未决状态的地方，知识包、基准存档、对局证据与离线测试只在旁边提供依据与验证。

唯一操作面

AI 只发现并执行 civ6 命名命令；.mcp.json 默认没有服务注册，Codex / Claude / Pi 都只是终端客户端。MCP 是 CLI 的内部通信实现。

单进程 = 单所有者

一个 civ6 debug 会话只拉起一个内部 MCP 进程、一次 initialize、一份 GameState；后续每条命令复用同一进程，终端命令不会重建状态。

内部协议不外露

call 与 tools 只作同会话协议兼容诊断；任意 Lua 仅 debug --developer；热座实验仅 debug --hotseat-seat/--hotseat-run。

离线资产不参与决策

知识按需只读查询，基准与对局证据只读保留；离线测试覆盖运行层，但“离线通过”不等于“实机通过”。

02
Runtime Layers

运行时分层：七层单向栈，每层一个主职责

从调用面到引擎，每一层只做一类事：CLI 面把命令翻译成内部调用，工具层管参数与串行，状态层管领域准备与阻塞判断，确认层拥有未决请求，Lua 层只构造与解析，传输层只负责一次请求一次响应。lua/、narrate、snapshot 没有向上依赖，因此整张依赖图无环。

CLI 只翻译，工具面不做业务

CLI 的 142 个命名命令是纯翻译层；server.py 的 90 个工具只负责参数、工具锁、门禁顺序与结果文本，领域准备下沉到 game_state.py，避免同一规则出现两份实现。

确认所有权唯一

ActionLifecycle / TurnProgress / DiplomacyProgress / CongressProgress 各持有一类未决；兼容私有属性只代理同一份状态，不保留副本。

失败不追认

丢回应、超时、身份未知一律保留未决；读取旧状态不触发自动重发，展示文案不承担完成判断。

03
Module Graph

模块图：依赖边来自真实 import

这张图不是按目录画的，而是按 src/civ_mcp 里的真实 import 关系画的：server.py 只直接依赖 connection / game_state / logger / snapshot；外交、议会、检查点、进程控制都在 GameState 的对应分支里懒加载，只在需要时进入；客户端只出现在最左侧的终端层，不进入依赖图。

入口薄、状态厚

cli.py 与 devtools/ 合计约 2k 行，只做参数翻译与证据落盘；约 4.9k 行的 server + game_state 才是行为主体。

Lua 是最大的一块

lua/ 48 个模块、18,694 行，几乎与其余 Python 等量：每个游戏领域都有一份构造器与解析器。

脚本另起进程

scripts/ 下的 relay、热座与验收驱动都不进入运行时 import 图；它们通过 CLI 或 stdio MCP 从外部驱动同一套工具。

04
Action Lifecycle

动作生命周期：单次提交，有界只读确认

所有普通动作都走同一个 ActionLifecycle：提交前用 prepare_scope 绑定 civ / seed / turn / owner 四字段；提交时只发一次，并在 Lua 内做二次 scope 守卫；之后只用只读查询回读证据。证据命中才退役，丢回应则保留原请求。

为什么先赋值 pending

提交在写操作前就把 pending 挂到 owner 上：即使执行抛错，也一定有人对这次尝试负责，避免“可能已执行但没人知道”的空档。

未知不遮蔽，原值不追认

scope 四个字段独立判断：某字段未知就跳过，不能遮蔽其他字段的真实变化；一旦有效值不匹配就永久置位失效，返回原值也不能解除。

同一动作的唯一出口

确认、精确 pre-entry 拒绝、显式会话替换是仅有的三条清除路径；其余一律保留未决。

证据因动作而异

移动保留 MOVE_WITNESS，攻击保留 pre_hp / fingerprint，建城保留 position + 查询串；确认只读，绝不调用提交语句。

05
Turn Progress

回合推进：观测面与请求面共用一套阶段解释

回合推进不是“点一下 Next Turn”：get_turn_status 与 end_turn 共用 read_turn_status、外交/议会/弹窗探针，但只有 end_turn 会建立 pending。确认三条件是：回合增长 + ready + 原世界身份匹配，缺一即保留未决。

三条件确认

turn_after > from_turn、ready（active 且 complete 且 ui=False）、world 匹配，三者同时成立才算推进；任一读失败只影响诊断，不改写已确认事实。

预算不是死锁判据

180s 轮询上限只是观察预算；超时返回 WAITING 并保留请求，与真实读取失败分开统计。

阻塞要模型自己解决

生产、科研、政策、单位、议会、外交、弹窗等阻塞都映射到具体工具，推进工具只报告不代选。

本地被重开是有效结局

收到原生 TURN_REOPENED 证据时按 REOPENED_LOCAL 处理并退役本次尝试，而不是继续等待或重发。

06
Wire Sequence

端到端时序：一次动作在六个进程角色之间的往返

以命名命令 unit move 为例：模型执行 CLI 命令，CLI 经内部 stdio MCP 把请求送进工具锁、门禁、领域准备、Lua 构造与 FireTuner；回执按 uuid 前缀匹配；确认阶段是另一串只读往返。整条链上只有一个地方能“再次提交”——而代码里没有这样的地方。

消息包络

每个请求被包上唯一 uuid，只接收带本请求前缀的行，以 CIVMCP|<uuid>|END 作为完成标记。

确认不提交

确认循环只执行 pending 里预先准备好的只读查询；这也是“同意图重入只确认”的实现基础。

未知分支显式存在

结果未知不是异常路径，而是正常状态：请求保留、模型获得指引、后续调用只确认旧请求。

07
Session & Checkpoints

会话替换与检查点：三态判定与两条门禁

换档、读档、冷恢复是三类显式替换，共用同一套加载确认。GameState 是唯一替换所有者；replacement_pending / save_pending 在证据链走完前一直保持——而“只有调用前可证明未调用，才允许 not_submitted”是这套状态机的铁律。

进调用后只能 unknown

一旦原生调用已进入，任何异常、取消、断线都只能是 unknown 并保持门禁；not_submitted 只用于调用前就能证明未发生的路径。

保存的完成证据

原生 SaveComplete + 指纹变化且 size>0 + 复检指纹仍一致，三者都要满足才算保存完成。

检查点绑定轮次

名称、sha256、文明、种子、回合、run_id 组合成检查点记录；只有加载原始基准才轮换新的测试轮次。

遗留模块

autosave.py 已无调用方，自动存档猜测被显式禁用——这条也写进了规格。

08
Domain Machines

领域状态机：外交交易与议会，各一套专用所有权

外交与交易各有专用 Progress（DiplomacyProgress / IncomingAttempt / TradeAttempt），却共用同一套 observer 与 nonce；世界议会则把原生阶段与本地请求状态拆成两个正交维度，再用三态解释统一查询、打开与投票。

身份仲裁是三值逻辑

身份完整且不同 → scope_invalid 永久失效；身份缺失 → 仅本次不能确认；返回原身份不能解除已锁存的失效。

零提交也要回执

来约的 ZERO 回执必须与 finish(zero=True) 一起 CONFIRMED，才能报告“未提交”；仅凭界面没变化不算。

议会三态同源

CHOICES / EMPTY / UNKNOWN 由同一个 HasChoices 复算：无提案时不走开始路径，以免原生 UI 自动提交与显式票计划重复。

REGISTERED 的破例

已登记的票单只能由显式 end_turn 放行；confirm 每次先把本地 state 重置为 UNKNOWN，不照搬普通动作的同回合严格规则。

Design Rules

八条设计规则：这套系统为什么长这样

把上面所有机制压缩成八条规则。它们不是口号：每一条都能在代码里找到对应的实现位置，也都能在 docs/ 里找到对应的验收记录。

先读真实状态

回合、坐标与实体 ID 必须来自真实游戏状态；不可见、未知与不存在要分开对待。
