# 当前架构

目标：本机让模型通过 MCP 玩 Civilization VI，保留游戏操作能力。

```text
MCP 客户端
  │ stdio JSON-RPC
  ▼
server.py：参数、工具入口、结果文本
  ▼
game_state.py：领域 interface、查询、存档替换
  ├─ actions.py：动作提交与确认
  └─ end_turn.py：推进请求与确认
  ▼
lua/：按游戏领域构造与解析 Lua
  ▼
connection.py / tuner_client.py：FireTuner 通信
  │ TCP 127.0.0.1:4318
  ▼
Civilization VI
```

游戏规则由引擎执行。GameCore 提供状态读取，InGame 发出操作，FrontEnd 提供主菜单读档。领域查询和动作保持独立，工具返回必要事实和回读结果供模型决策。

动作按「单次提交 → 有界只读确认」执行。`ActionLifecycle` 唯一持有未决动作，共用提交、回应解释、明确拒绝、未知保留和确认过程；GameState 负责领域准备与结果叙述。移动、攻击、建城、生产及城市射击保留各自证据，listener 仍核对来源并只清理自身。相关依赖操作、保存和推进先核对结果；读取旧状态或丢失回应不触发自动重发。兼容私有属性只代理同一份状态，不保留副本。

`TurnProgress` 唯一持有未决推进、起始回合和原始差分快照，通过明确的 `TurnContext` 协作获取事实与报告，不读写 GameState 的任意私有字段。普通概览更新观察缓存不会替换原请求基线；陈旧或未来快照不得生成错误差分，报告读取失败也不重新发送已确认推进。`turn_pending` 提供只读门禁事实。

`end_turn` 只检查阻塞、发起推进并确认结果；需要生产、科研、外交、占城或议会决策时，由模型调用相应工具。无需反思 payload 或日记前置步骤。回合数字变化后还需确认本地玩家可操作；外交回应后继续确认原来的推进请求。

GameState 拥有完整的会话替换过程；`game_launcher.py` 负责原生进程操作，`game_lifecycle.py` 负责原生菜单、加载和文件事实。MCP 生命周期工具只委派，不写入 GameState 私有门禁、重置会话或清理索引。正常换档 `reload_game_save` 与显式完整重启 `restart_and_load` 复用同一个加载和完整状态验证流程。快速路径退出前校验检查点及未决操作，提交一次 `ExitToMainMenu`，以原生 `UI.IsInFrontEnd` 确认前端，再清理旧会话缓存、动作绑定和保存列表索引。Lua 目录中的 MainMenu 或 GameCore 索引不单独作为前端事实；加载的原生块再次校验前端。菜单返回上限 30 秒，计入总加载 180 秒；未知、取消或超时保留替换门禁，不重发退出／加载或自动完整重启。完整新快照、身份、回合、最终就绪及目标文件全部核对后才释放门禁。`reset_session` 清理旧缓存和动作／推进状态时保留替换门禁，`replacement_pending` 只表示替换未知，保存未知单独处理。原生转换使用 `NativeTransition` 状态、进程操作使用 `ProcessResult` 事实控制顺序，展示文案不承担完成判断。通信失败不触发隐藏的游戏重启或动作重放；动作结果未知时先回读确认。

保存同时核对原生 `SaveComplete`、精确新文件及身份回合；`checkpoints.py` 将已确认检查点绑定文件指纹和本轮标识。每次验证加载原始基准才建立新轮次，MCP 重启保留轮次，其他轮次的文件不作为恢复兜底。

日志仅用于本地问题追踪，不参与玩法决策或回合放行。服务不启动网页、云同步、后台镜头、弹窗轮询或终局监测任务。

离线测试只收集 `tests/`。`integration_turns.py` 通过 `mcp.client.stdio` 和 `ClientSession` 启动同一 MCP 服务，复用实际工具的执行、回读与生命周期入口，不另建底层控制路径。驱动的固定策略只处理常见阻塞，异常和结果未知时停止；总时间与每回合处理次数有上限。实机验收需要固定存档并检查动作、阻塞、回合推进和显式恢复。

`open_world_congress` 独立于纯查询，在已确认的原生投票阶段、存在可投选择且本阶段未提交时，执行 Intro 的 DequeuePopup → ShowWorldCongress 开始路径。开始前记录文明、种子、回合及阶段；已请求或丢应答只核对可见状态，不重复事件。原普通推进未决时可以打开议会，其他未决动作、保存及加载门禁保持。无选择或未知提案不走开始路径，以免原生 UI 自动提交与显式票计划重复。

议会查询、显式打开和显式票单共用原生阶段与提案可投资格解释。`proposal_status` 的 `CHOICES` 表示存在可投提案，`EMPTY` 表示没有可投提案（可能仍有禁投行），`UNKNOWN` 表示资格未核实；resolutions 另行按当前阶段处理，Stage2 不重投旧决议。共享解释不合并三种操作，也不引入默认投票。
