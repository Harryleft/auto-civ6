# 灾害、恢复读取与分数差异修复规格

基点 `788563a`；集成分支 `codex/turn-50-reliability`。2026-10-17，标签 `ready-for-agent`。用户授权先查原因、to-spec 成文、implement-spec 实施、离线和实机验证；沿用既有测试边界，保留所有现有存档，不 push。继续使用本地 tracker，无远端 issue／PR。

## Problem Statement

第 49→50 回合洪水弹窗使确认等待 180 秒；关闭后报告快照与通知不可用，恢复后概览看似成功但下一次读取连接拒绝。原生总分保存前 72、加载后 76，被概览当作无说明的单值。

原因调查使用同轮归档第 49 回合重放，并保留失败尝试：灾害持有 PopupManager 事件引用，原生 Close 才释放；等待流程只识别外交，不识别可见信息弹窗。单位快照误用 GameCore，远程目标检查需要的 UnitManager.CanStartOperation 在该上下文为 nil，在 InGame 可用；错误导致未完成流被废弃，却被可选快照吞掉。关闭工具另有 50..199 无依据索引盲扫及回调失败仍报成功的问题。

分数在保存前同一原生请求中已不一致：GetScore=72，GetCategoryScore 的有效分类为市政21、帝国18、科技16、时代21（合计76）。恢复后总分76、相同分类。能定位为引擎总分与分类汇总在运行／重载边界不同步，不能据此确定未公开的 C++ 缓存更新实现。MCP 没有自行计算旧总分。

## Solution

及时报告可显式关闭的信息弹窗，保留原推进请求；通过已发现的对应弹窗状态调用原生关闭函数并确认结果。单位快照统一使用 InGame，恢复成功要求完整必要状态读取。概览同时提供原生总分、原生分类及一致性信息，新检查点保存该证据，恢复时说明差异，避免将分数汇总刷新误报为玩法状态全部一致。

## User Stories

1. 作为玩家，我希望灾害弹窗出现后及时得到具体阻塞原因，以便关闭后继续。
2. 作为玩家，我希望由我显式关闭信息弹窗，以便保留操作选择权。
3. 作为玩家，我希望关闭后确认原推进请求，以免重复推进。
4. 作为玩家，我希望引擎未就绪时仍能发现可见弹窗，以免误等满超时。
5. 作为玩家，我希望正常 AI 处理不被误判为已完成，以免在旧回合操作。
6. 作为玩家，我希望未知可见性保持未知，以免擅自放行。
7. 作为玩家，我希望外交、贸易、议会选择仍由我处理，以免关闭工具替我决策。
8. 作为玩家，我希望工具在弹窗自己的状态调用原生回调，以便释放事件锁。
9. 作为玩家，我希望缺失弹窗状态被如实报告，以免盲扫造成大量重连。
10. 作为玩家，我希望关闭失败不被描述为成功，以便继续处理真实阻塞。
11. 作为玩家，我希望单位有行动力时快照仍可读取，以免回合报告失败。
12. 作为玩家，我希望概览后的单位、城市读取连续成功，以免需要手工等端口恢复。
13. 作为玩家，我希望只有完整读取后才报告 Loaded，以便恢复结果可用。
14. 作为玩家，我希望部分读取失败时保留恢复门禁，以免用不完整状态继续动作。
15. 作为玩家，我希望断流后不自动重放操作，以免重复执行。
16. 作为玩家，我希望仍能看到引擎官方总分，以便与游戏对照。
17. 作为玩家，我希望看到原生分类分，以便解释总分差异。
18. 作为玩家，我希望分类缺失明确未知，以免误判为零或完整。
19. 作为玩家，我希望总分和分类不一致时得到提示，以免把旧汇总当成当前完整证据。
20. 作为玩家，我希望新保存绑定分数证据，以便恢复前后可追溯。
21. 作为玩家，我希望恢复时知道总分变化及分类是否一致，以便区分汇总差异与状态差异。
22. 作为玩家，我希望旧检查点仍可恢复，以免本次升级破坏已有成果。
23. 作为玩家，我希望基准和所有既有存档保持原字节，以便继续复核。
24. 作为维护者，我希望回归测试只使用现有 seam，以免新增游戏控制实现。
25. 作为维护者，我希望实机证据保留失败及修复后的记录，以便验证真实改进。

## Implementation Decisions

- 回合确认增加有界只读可见信息弹窗探针，目标响应在正常接口延迟下不超过 15 秒；不自动关闭、不重发 ACTION_ENDTURN、不放宽引擎和 UI 就绪门槛。正常处理、ready=false、UI回合暂不同步、缺失 API 均覆盖。
- 关闭流程仅处理明确已知的信息弹窗；使用发现目录按精确名称定位，调用前核对 ContextPtr ID、可见性及原生关闭函数。目录缺失最多一次有界重新发现，禁止猜索引。回调成功且关闭证据成立才报告 Dismissed；队列有上限，残留明确报告。不得清空私有队列来伪造成功，不新增后台轮询。
- 单位快照在与公开单位查询相同的 InGame 执行。加载确认在既有总预算内要求 overview、单位和城市快照成功且与当前身份／回合一致；失败保留 pending_load，只重试只读确认，不重放 load。
- 保留 GameConnection 响应关联、统一预算及未完成流废弃规则；不以全局自动重试掩盖 Lua 错误。
- 概览通过原生分类接口读取所有正权分类，保留官方总分。只有完整有效分类可计算诊断合计；不乘两次权重，不手算游戏评分公式，不替换总分。格式错误、重复或部分分类不得作为完整证据。
- 新检查点附加可选的原生总分／分类证据，并与原有哈希、身份、回合、run 绑定。旧检查点无此信息仍按原有身份门禁加载，并明确缺少保存时分数证据。分数一致不能代替城市、单位等状态验证。
- 恢复结果对比原生总分和分类，原样报告差异；分类一致而总分变化时说明该观察，不断言未公开缓存内部实现。不得为凑分写引擎或改存档。

## Testing Decisions

沿用用户已确认的 GameState／FakeConn、内存 FireTuner 字节流、快照差分、临时存档目录与原生 MCP seam。测试外部行为：及时阻塞、一次提交、保留 pending、真实关闭证据、连续只读结果、完整加载证据、分数信息不丢失及缺失不假定一致。原生重载评分实现无法离线模拟证明，以真实配对查询验证，不宣称修复游戏二进制。

先失败后最小实现，各项独立 worktree；集成后 uv sync --locked、全量 pytest、compileall、diff check。Standards／Spec 并行独立审查，处理全部实质问题。

实机使用同一原始基准对局的已验证 T49、T36 归档重放洪水／沙尘暴；原件不覆盖。观察提示→显式关闭→确认原请求，核对快照／通知与紧邻概览、单位、城市读取。新命名结果保存后显式重启恢复，立即连续读取，并核对身份、回合、城市、单位、分类分与官方总分差异。至少一次带保存前不一致证据的配对重载；保留完整 MCP 调用、指纹和失败记录。
