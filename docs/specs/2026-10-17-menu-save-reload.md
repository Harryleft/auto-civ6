# 返回主菜单后加载存档规格

2026-10-17。基点 `b148ff7`，集成分支 `codex/menu-save-reload`。本地 tracker，标签 `ready-for-agent`；沿用此前已确认的测试边界，无远端 issue／PR、不 push。用户授权实施菜单快速路径，完整重启保留为故障恢复，离线及实机比较、状态清理和保存恢复验证全部完成。

## Problem Statement

目前显式恢复入口会结束 Civ6 进程再启动。上一轮4次加载耗时62.214～66.601秒，正常换档也承担启动过程。已有菜单加载与完整状态核验，但缺少从正在运行的对局安全返回菜单的接口。

本机游戏菜单和官方自动化以 Events.ExitToMainMenu 返回主菜单，并以 UI.IsInFrontEnd 确认。目录中出现 MainMenu 或没有 GameCore 索引都不足以单独证明转换已完成；返回后旧 Lua 索引、快照、地图基线和动作绑定必须失效。

## Solution

新增 `reload_game_save(save_name)`，用于正常换档：验证目标检查点、拒绝未决操作、只提交一次返回菜单、确认原生前端、清理旧会话、复用已有原生加载及完整验证。游戏进程保持运行。`restart_and_load` 保持显式完整重启职责；菜单失败不自动杀进程。

## User Stories

1. 作为玩家，我希望正常换档不结束游戏进程，以便减少启动等待。
2. 作为玩家，我希望明确区分正常换档和故障恢复，以便选择合适入口。
3. 作为玩家，我希望保留完整重启入口，以便进程挂起或失联后恢复。
4. 作为玩家，我希望目标文件在离开当前对局前被验证，以免无效文件导致白白退出。
5. 作为玩家，我希望只能加载明确命名的已验证检查点，以免误选自动存档。
6. 作为玩家，我希望原始基准不可覆盖，以便保留测试来源。
7. 作为玩家，我希望未决动作或保存／加载／推进得到明确拒绝，以免丢失未知结果。
8. 作为玩家，我希望返回菜单只发一次，以免在新界面重复执行。
9. 作为玩家，我希望响应丢失后只确认菜单状态，以免重发退出或加载。
10. 作为玩家，我希望原生前端确认后才加载，以免旧对局状态尚未卸载。
11. 作为玩家，我希望旧 Lua 索引不被复用，以免发到错误上下文。
12. 作为玩家，我希望已在菜单时直接加载，以免多执行一次退出。
13. 作为玩家，我希望菜单等待有上限，以便尽快获知失败。
14. 作为玩家，我希望总加载等待有上限，以免分阶段无限累加。
15. 作为玩家，我希望菜单失败不触发隐藏完整重启，以免多次替换会话。
16. 作为玩家，我希望旧快照、地图基线及身份缓存被清理，以免污染新状态。
17. 作为玩家，我希望旧动作、推进和保存绑定不被带入，以免错误门禁或误报完成。
18. 作为玩家，我希望保存列表的旧索引失效，以免旧清单被当作新会话清单。
19. 作为玩家，我希望加载成功必须取得本次完整单位和城市快照，以便立即继续操作。
20. 作为玩家，我希望加载后核对文明、种子、回合和可操作状态，以免接错存档。
21. 作为玩家，我希望新检查点的分数分类对照继续工作，以便如实解释原生总分差异。
22. 作为玩家，我希望旧检查点继续兼容，以免升级破坏之前成果。
23. 作为玩家，我希望正常换档保持同轮检查点所有权，以免原有恢复点失效。
24. 作为玩家，我希望新保存能够通过菜单路径恢复，以便验证闭环。
25. 作为玩家，我希望耗时对比使用相同起点和目标，以便判断真实收益。
26. 作为玩家，我希望记录 PID 和恢复后状态，以便证明进程保留及旧状态清理。
27. 作为维护者，我希望使用同一 MCP／连接／加载验证实现，以免新增游戏控制路径。
28. 作为维护者，我希望所有既有存档保持原字节，以便后续复核。

## Implementation Decisions

- 正常入口新增 reload_game_save，显式 save_name 必填；现有菜单入口保持菜单语义，restart_and_load 保持完整重启语义。工具说明和操作文档引导正常换档优先新入口。
- 在任何退出前校验文件名、当前轮次、文件哈希和预期身份／回合。未决 action、save、load、end_turn 均拒绝快速替换，不增加绕过参数；需要放弃未知结果时继续由用户显式完整恢复。
- 生命周期模块提供原生前端只读确认和单次 ExitToMainMenu。确认值必须是严格布尔；缺失、错误、重复或无效响应保持未知。只使用当前连接发现的上下文，不猜索引，不用 OCR、鼠标或 Network.LeaveGame／LoadGame 连发替代原生流程。
- 旧世界目录索引不是前端事实，必须重新发现并确认 UI.IsInFrontEnd 为 true。发送 Network.LoadGame 的原生块内再次确认前端，防止查询后界面变化。
- 退出与加载组成一次串行会话替换；提交退出前建立门禁，确认菜单后调用既有 reset_session 并清除旧保存列表索引。加载后建立新快照及身份；同文明同种子同回合也必须重建，不复用旧缓存。转换未知时保留门禁，不能假称旧世界仍可操作或新世界已就绪。
- 共享现有加载总预算180秒，菜单返回子预算最多30秒且包含在总预算内。查询／发现耗时计入；退出和 Network.LoadGame 各至多一次，异常不重放，不自动启动第二轮操作。
- 复用原生保存枚举完整条目、自动 Continue、严格完整快照、加载前后文件核对、分数对比和轮次规则。旧菜单入口也以原生前端事实确认；不复制一套加载器。
- 成功只在同一文明／种子／回合、完整快照、最终就绪和目标文件均通过后返回。明确未提交的失败如实报告；有可能提交的超时／断流保持未知，提示可显式完整恢复。
- 进程 PID 和耗时由实机验收客户端及本机只读进程查询记录，不给运行时引入平台 PID 依赖、后台观测器或性能框架。

## Testing Decisions

沿用已授权的 MCP 工具→真实 GameState／FakeConn、内存 FireTuner 字节流、快照差分、临时存档目录及 launcher 隔离边界。按公开外部行为做红绿切片：合法换档、同回合重载、已有菜单、错误目标、未决拒绝、前端未知、旧目录残留、一次提交、断流确认、超时门禁、状态清理、严格新快照、旧入口兼容、显式完整重启不变。测试不得连接真实游戏；PID 仅实机测量。

集成后 uv sync --locked、全量 pytest、compileall、diff check，Standards／Spec 两轴独立审查并修复实质问题。

实机只使用同一 benchmark_turn_1 对局的已验证第37、50回合存档，原件不覆盖，不推进回合。两条路径分别执行相同顺序50→37、37→50；每个目标至少一组菜单／完整重启对比，记录总耗时、进程PID、文明／种子／回合、单位／城市／区域／分类分及连续读取。两组只能作为本机本次观测，不推导普遍性能保证。验证从50换至37时单位、研究与地图基线重建，再换回50，核对同回合重载也无缓存复用。另保存独立命名结果并通过菜单路径恢复，保留结果文件和哈希；最终停在新的第50回合结果。失败尝试同样记录，必要补修后重测。

## Out of Scope

不优化地图自身加载或游戏二进制，不跳过完整状态核验来凑速度；不增加自动故障升级、自动选档、批量策略或第二游戏控制；不修改原生评分机制，不推进新的游戏回合；不覆盖／删除既有存档，不 push、不创建远端 issue／PR。
