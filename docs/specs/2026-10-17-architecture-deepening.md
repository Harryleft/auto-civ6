# 四项架构深化规格

状态：ready-for-agent。固定基点：ce1e843242420d7ac79ed5f9bfe0129a5e186ed1。集成分支：codex/architecture-deepening。沿用现有本地 Markdown tracker，不创建远程 Issue 或 PR，不 push。

## Problem Statement

连续调度修复已经建立单次提交、有界确认、未知保留和菜单快速换档保证，但动作生命周期在四类调用中重复，存档替换由工具调度维护私有状态，回合推进借用整个 GameState，议会阶段与选择事实存在多处解释。继续修复时需要跨 module 理解隐含顺序，容易使一个入口遗漏规则。当前基点 897 项离线测试通过；这是架构摩擦，不等于四处均有新的实机缺陷。

## Solution

在现有 MCP → GameState → Lua → FireTuner → Civ6 调用链上，集中四项领域知识的所有权，提高 module 的 depth、locality 和 leverage。保留工具名称、参数、显式游戏决策与现有恢复行为；不把重构变成更多转发 module 或后台机制。四项进入同一个集成分支，互不依赖的任务并行，共享状态和冲突由集成验证统一处理。

## User Stories

1. As a 玩家, I want 移动请求最多提交一次, so that 丢失回应不会导致重复行动。
2. As a 玩家, I want 攻击提交与伤害确认分开, so that 估算不会被当作真实伤害。
3. As a 玩家, I want 建城等待真实归属城市, so that 旧状态不会触发重发。
4. As a 玩家, I want 生产以实际队列或区域落点确认, so that 未决转产不会被错误越过。
5. As a 模型客户端, I want 同一未决意图只进行回读确认, so that 重复调用不会产生新写入。
6. As a 模型客户端, I want 确认包含文明、种子、回合和实体, so that 旧对局证据不会确认新动作。
7. As a 玩家, I want 明确的未提交拒绝释放动作门禁, so that 可以重新决策。
8. As a 玩家, I want 可能已提交的动作保留未知状态, so that 后续依赖操作不会基于猜测继续。
9. As a 维护者, I want 动作共同过程由一个 module 拥有, so that 修改一次可以覆盖所有已跟踪动作。
10. As a 维护者, I want 移动和城市攻击保留各自原生 witness, so that 通用编排不会削弱领域证据。
11. As a 玩家, I want 正常换档返回主菜单并保留进程, so that 无需重复播放启动流程。
12. As a 玩家, I want 完整重启保持显式故障恢复入口, so that 菜单路径失败不会暗中杀进程。
13. As a 玩家, I want 加载门禁在任何清理和身份重置期间持续有效, so that 未确认替换不会放行游戏动作。
14. As a 玩家, I want 加载确认比较目标文件、身份、回合和完整新快照, so that 旧会话数据不会冒充恢复成功。
15. As a 模型客户端, I want 菜单退出和加载各最多提交一次, so that 取消、超时或断线不会重放。
16. As a 维护者, I want 存档替换结果用事实控制顺序, so that 展示文案变更不会影响门禁。
17. As a 维护者, I want MCP 只调度并呈现加载结果, so that 不再直接维护游戏私有状态。
18. As a 玩家, I want 回合推进只发送一个原生请求, so that 外交或议会暂停后仍能确认原请求。
19. As a 模型客户端, I want 回合号变化且本地玩家就绪后才报告完成, so that AI 处理期间不会误放行。
20. As a 玩家, I want 快照或通知读取失败只限制报告, so that 已确认推进不会重新发送。
21. As a 维护者, I want 推进请求和起始回合由同一 module 拥有, so that 无需跨文件维护私有字段协议。
22. As a 模型客户端, I want 议会查询仍然纯读, so that 读取议题不会打开界面或提交。
23. As a 玩家, I want 显式打开议会仅在确有选择时开始, so that 空阶段不会触发原生自动提交。
24. As a 玩家, I want 全部提案禁投时允许显式空计划, so that 阶段不会被错误阻塞。
25. As a 模型客户端, I want 查询明确区分有原始提案与有可投提案, so that CHOICES 不再需要额外猜测。
26. As a 玩家, I want 可投提案和未知资格仍禁止隐式投票, so that 重构不会替我做策略决定。
27. As a 维护者, I want 议会阶段在查询、打开和投票使用相同解释, so that 修改规则不会产生入口分叉。
28. As a 维护者, I want 测试跨真实 GameState 或 MCP interface, so that module 内部重构不会迫使测试复制实现。
29. As a 维护者, I want 关键 Lua 时序在隔离环境实际执行, so that 文本包含断言不会冒充行为验证。
30. As a 玩家, I want 原始基准、现有存档和第 100 回合结果完整保留, so that 架构调整不会损失验收成果。

## Implementation Decisions

- 动作提交与确认 module 统一拥有已跟踪动作的锁存、单次提交、明确拒绝、未知保留、确认和清理。现有领域动作只提供自身证据和响应解释；不为尚未跟踪的工具扩展自动提交系统。
- 提交前的新鲜 scope、原生块内竞态校验、listener 归属与清理保持；已知同意图只能确认，不重新生成原生请求。保留城市攻击和移动不同 witness，不强行统一原生事件。
- 保留现有 GameState interface。可在其 implementation 内收拢状态和私有过程，不以全量迁移类、通用策略插件或跨游戏框架作为完成条件。私有兼容代理仅在现有调用／测试确有需求时保留，不能成为新状态副本。
- 存档替换由 GameState 所属 module 负责完整顺序和门禁；MCP 不再安装、恢复或清除加载私有标记，也不直接清索引。菜单和完整重启复用同一加载确认。原生转换结果有明确事实值，业务流程不再匹配成功／拒绝的展示文案。
- 保留菜单 30 秒、完整加载 180 秒的现有总预算；重连只服务只读发现和确认，不重发退出、加载或游戏动作。异常、取消或超时后保留未知门禁。
- 回合推进 module 拥有未决请求和起始回合；GameState 的保存／动作门禁消费统一事实。推进实现通过有意设计的现有 interface 读取事实、获取报告，不再把任意私有字段当作契约。
- 普通只读观察发现对局身份变化时，只清理观察缓存；已有未决推进保留门禁并标记来源失效，不以新对局状态确认旧请求。旧请求仅在已确认推进／终局，或显式受保护的会话替换清理时退休。
- 原生加载调用一旦进入，调用异常不足以证明未提交，必须保留 unknown 与门禁；not_submitted 仅用于原生调用前能够证明未调用的拒绝。
- 回合报告保持为已确认推进的展示；快照失败不得重新建立请求。外交、交易、议会、灾害弹窗仍要求模型显式处理。
- 议会 module 内共享原生阶段和提案可投资格解释。查询给出可投、不可投和未知事实；如保留原始行存在信息，名称与叙述必须明确区分。Stage2 不重投旧 resolutions。三种操作不合并成隐式策略流程。
- 不改变检查点文件格式和既有 run_id／指纹约束；不修改游戏存档和旧验收文档。新的规格、tracker 与离线验收独立记录。
- 保留已有传输 module 的请求关联、串行、上下文发现、超时隔离与无重放保证。本次不重写通信协议。

## Testing Decisions

- 沿用用户此前确认的最高可用 seam：MCP／真实 GameState 配现有 FakeConn／Engine adapter、内存 FireTuner 流、Lua 5.1 执行 adapter、快照差分和临时存档目录；不增加真实游戏控制路径。这是既有测试授权的延续。
- 好测试断言 interface 的可观察结果、未决操作允许／拒绝和外部原生请求；不 mock 自有状态机，不以私有字段形状或源码包含片段替代行为证明。
- 动作保留并加强延迟、旧状态、响应丢失、重复调用、明确未提交、身份／回合变化、依赖操作阻止、原生 witness 清理场景；至少一处关键 Lua listener 行为由隔离执行覆盖。
- 生命周期保留菜单快速路径、完整重启、一次加载、瞬断、旧快照拒绝、状态清理、文件变化、取消和预算；至少使用真实 GameState 经既有工具入口验证门禁连续性。
- 回合保留就绪、未知、外交／议会暂停、确认原请求和报告失败行为；增加／迁移关键测试使其跨真实 GameState，减少复制完整 FakeGameState 的依赖。
- 议会通过实际 Lua 执行验证阶段／查询／打开／票单一致性，覆盖全禁投、混合、单向禁投、未知和 Stage2 旧决议；只读调用不产生打开、投票、提交或继续。
- 每个 ticket 使用 tdd；结构重构先由现有行为测试锁定，再以缺失行为测试红绿验证。删去已由行为覆盖的脆弱断言，不能机械叠加测试。
- 集成门槛：锁定依赖同步、全量离线 pytest、编译、diff 检查、Standards／Spec 独立双轴审查与修正。审查固定范围为本规格基点至最终集成 tip。
- 本次不连接真实游戏，不宣称新实机回合／保存恢复验收。已有实机成果只作为被保留证据。

## Out of Scope

网页、云同步、后台轮询、日志协议、自动重启／重放、玩法策略、通用操作账本、全项目重写、新远程发布、push、修改旧存档或旧验收证据、重新推进回合。没有证据收益的纯文件拆分不作为成果。
