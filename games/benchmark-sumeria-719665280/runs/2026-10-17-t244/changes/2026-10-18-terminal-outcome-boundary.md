# 终局续测：权威胜利类型与保存边界

标签 ready-for-agent；本地 Markdown tracker；基点 `1a59327`，集成分支 `codex/architecture-deepening`。

## Problem Statement

第 244 回合原生界面已显示苏美尔失败、瑞典科技胜利，工具却报告 Unknown。两个查询忽略原生胜利类型，随后用进度猜测；附加科技需求 33.5 还会触发整数解析异常。终局窗口中的一次保存没有完成，产生持续未知，无法正常菜单换档。

## Solution

终局类型直接取官方胜队与胜利类型，不再由分数、进度或接近阈值推断。已证实终局时，工具明确拒绝新的保存请求，保留终局前已确认检查点与原生终局证据。旧未知仍保留，只能按既有显式故障恢复流程替换对局。

## User Stories

1. 作为玩家，我希望科技胜利与原生界面一致，以便知道真实终局原因。
2. 作为玩家，我希望其他原生胜利类型同样准确，以便不依赖局部进度猜测。
3. 作为玩家，我希望同队不同玩家的胜利仍按队伍判断，以便不把队友胜利误报为失败。
4. 作为玩家，我希望原生类型缺失时保留 Unknown，以便不生成未经证实的结果。
5. 作为玩家，我希望 33.5 或畸形附加进度不能破坏权威结果，以便查询稳定。
6. 作为玩家，我希望两种查询上下文给出相同事实，以便回退不会改变终局类型。
7. 作为玩家，我希望终局保存立即明确拒绝，以便不陷入可避免的未知锁存。
8. 作为维护者，我希望拒绝发生在原生监听和请求之前，以便零副作用。
9. 作为维护者，我希望旧未知保存仍优先门禁，以便新代码不会追认旧请求失败。
10. 作为玩家，我希望普通活动回合的单次保存与双证据确认保持可用，以便保留恢复能力。
11. 作为测试者，我希望从本轮第 244 回合检查点重放终局，以便核对原生结果与新保护。
12. 作为玩家，我希望保留全部旧存档、现有结果和终局截图，以便验收可复查。

## Implementation Decisions

- 复用当前终局查询、GameState 保存和原生保存接缝，不新增服务或状态机。
- 两个终局查询采用官方 GetWinningTeam 的 winningTeam 与 victory selector，按原生 Victories 映射读取 VictoryType。胜负按本方 team 与 winningTeam 比较；展示玩家不得替代队伍身份。异常或未映射保持 Unknown。
- 删除终局类型的 TestVictory、接近宗教多数、分数默认值、进度阈值猜测及 Python 二次改写；进度仍留在独立进度查询，不能覆盖权威结果。保留已淘汰本方等既有终局识别，不凭回合阈值发明胜利类型。
- 新保存请求在已确认终局时返回明确未提交，不注册新 SaveComplete、不发送 Network.SaveGame、不设置新 pending_save。必要同帧原生保护也须在监听和请求之前。未知胜利类型不影响已确认终局保护。
- 此为本项目确认活动回合的保存边界，不能宣称引擎全部终局或“再战一回合”永久不可保存；不自动关闭终局窗口、不释放暂停、不点击再战一回合。
- 旧 pending_save 优先现有门禁，不能依据无文件、终局事实或重建客户端清除。此次现场先经授权显式故障恢复至已验证第 244 回合；不能盲目重发旧保存名称。
- 终局前检查点与原生终局截图／日志组成结果资料；没有生成的终局后存档不得列为成功保存。

## Testing Decisions

沿用用户已确认的 GameState／FakeConn、真实 Lua 5.1、内存原生事件及临时存档目录；离线不连接游戏。

- 经公开入口与真实 Lua 覆盖科技、文化、宗教、外交、征服、分数映射；同队不同玩家、不同胜队、多成员展示及缺失／异常类型。
- 权威终局不被 33.5、畸形或矛盾附加进度破坏；高进度、旅游、近多数或积分不能生成正式类型。查询上下文回退一致。
- 新的已知终局保存零请求、零新监听、零新 pending；旧未知仍禁止后续保存和普通换档。普通活动回合保存仍一次提交并核实文件及原生完成。
- 全量离线、编译、diff 与独立双轴审查后，实机重放第 244 回合终局，核对类型、立即保存拒绝、无新文件、后续只读仍可用；保留原件。

## Out of Scope

改变游戏胜负、修改规则、延长终局、强制解除暂停、猜测缺失结果、重放旧未知保存、伪造终局后存档、删除存档、push。
