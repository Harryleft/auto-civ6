# 第 61～81 回合查询与展示修复规格

## Problem Statement

T61 验收发现：非就绪商人查询在原生检查全部拒绝后，回退枚举未相遇、未揭示及不可达城市；城市改良提示和建造者任务直接读取未揭示资源；通知只显示标题“失败！”，缺少原生主体摘要。模型需要可信的可用候选和必要详情，避免把隐藏信息或标题当成动态事实。

## Solution

按 P2 商路、P2 资源可见性、P3 通知详情的顺序集成。查询保持只读，原生合法性和本方可见性决定返回内容；无法确认时不扩大候选。通知补足原生摘要，不推断隐藏主体，不改变回合或终局门禁。离线完成后从同轮 T61 验证档续推至 T81，以获胜为目标继续检验决策与调度，保留现有成果及新结果。

## User Stories

1. 作为 Agent，我希望商人未就绪或容量不足时收到真实原因，而不是未经验证的城市清单。
2. 作为 Agent，我希望可选商路仅包含本方已知、原生当前允许的目的地，收益预览不构成可达证明。
3. 作为 Agent，我希望查询失败与合法空列表可区分，查询不会建立、迁移或结束商路。
4. 作为 Agent，我希望城市提示和建造者任务只使用本方已揭示资源，未揭示资源不影响任务分类或优先级。
5. 作为 Agent，我希望资源可见性 API 缺失或失败时保留未知，不把隐藏类型、数量或坐标作为行动依据。
6. 作为 Agent，我希望可见资源、修复及普通地形任务仍可使用；提示不承诺当前可执行。
7. 作为 Agent，我希望通知列表和回合报告均呈现必要原生摘要，区别未相遇城邦失败与本方失败。
8. 作为 Agent，我希望重复摘要只展示一次，旧通知协议仍能读取，换行或分隔符不破坏解析。
9. 作为维护者，我希望通知文案不控制原生行动分类、推进确认或终局判断。
10. 作为用户，我希望以同轮已验证存档继续 20 个净回合，正常恢复优先菜单路径，保存、恢复和状态清理均有证据。
11. 作为用户，我希望保留原始基准、全部旧存档及验收结果，新检查点独立命名，不 push。

## Implementation Decisions

- 商路入口取消“全部拒绝就枚举”的宽松回退；复用本机原生 UI 的候选规则，身份和地图已知过滤后，再检查原生当前可建。区分暂不可用、空、未知，维持公开参数契约；不新增调度器或推测性策略。
- 城市和建造者资源提示共用小型本方资源可见性解释，以本机原生玩家资源接口为准；隐藏资源按普通地形处理，不从底层资源类型生成资源任务。可见性未知时明确保守降级，不伪造可执行性。
- 通知模型增加可选摘要，协议兼容旧行，标题和摘要经过安全单行处理及本地化。列表与回合报告共用显示组合；不根据文本改变行动门禁。未相遇主体保持原生匿名；不补查隐藏身份。
- 续用当前集成分支，实施分支各自工作树，独立 merger 合入，之后独立 Standards／Spec 审查。仅纳入本次内容。

## Testing Decisions

沿用此前已确认的 GameState／FakeConn、Lua 5.1 执行、快照差分及临时存档目录，无新增测试边界。通过公开查询／报告行为验证，逐项 red→green，不用源码字符串断言代替查询执行。

商路覆盖非就绪、容量不足、已知合法目的地、未相遇、未揭示、不可达、原生读取失败及零写入。资源覆盖同一地块隐藏→揭示、城市／任务一致、普通地形／修复保留及可见性缺失失败。通知覆盖摘要主体、重复／空摘要、旧协议、特殊字符、列表与回合报告一致、原生门禁不变。

完整离线执行锁定依赖、全部 pytest、compileall、diff 检查。通过后以公开 MCP 手动逐步决策 T61→81，不调用固定策略批量脚本；记录每次原生确认、暂停、决策变化，T71 中间档和 T81 结果档，菜单恢复比对概览、单位、城市、政策、商路、着力点、外交、总督、单位活动和忠诚度。官方总分与分类向量分别保留。

## Out of Scope

不改胜利规则、游戏配置或历史战果，不使用隐藏对手信息，不新增固定文明策略、后台循环、网页控制、通用可见性框架或强制日志协议；不从基准重新开局，不覆盖旧档，不合并 main、不 push。
