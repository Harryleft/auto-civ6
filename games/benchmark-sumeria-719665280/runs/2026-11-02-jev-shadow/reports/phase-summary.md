## 按单位拆分决策

每回合需要检查局势及任务是否变化，并不要求每个单位都重新做一次开放式规划。正在执行且仍适用的商路、驻防、护卫或移动任务可以保留；受到新威胁、路径变化、任务完成或战略变化影响时，再做相应决策。判断任务是否仍适用也必须依据本回合事实。

| 单位 | 可交给 Jev 的有限局部选择 | 主模型保留的决策 |
| --- | --- | --- |
| 建造者 | 在明确城市目标与候选中比较维修、改良、下一步移动或等待 | 城市发展、收获时机、区域预留、多工分配、护卫、末次劳动力用途 |
| 开拓者 | 比较已圈定区域中的少量落城候选与路线 | 扩张方向、外交／忠诚度、落城时机、护卫与城市争地 |
| 军事单位 | 在批准的战术目标下比较攻击、撤退、治疗、守位 | 战争目标、集火顺序、占格、城市火力、可接受损失及掠夺风险 |
| 伟人 | 比较指定能力的候选激活地点或时机 | 招募预算、保留或使用、科技／市政配合、巨作容量和主题化 |
| 商人 | 按指定目的比较原生返回的目的地 | 商路容量、迁移起点、道路／外交目的、跨商人分配与战争风险 |

建造者动作应区分：普通／特色地块改良、连接资源、免费维修、移除地貌并收获生产、收获资源、拆除改良、移动或等待，以及满足原生条件后的特殊消耗。苏美尔金字形神塔属于地块改良；学院、图书馆等区域和建筑通常由城市生产，不能视为建造者的通用建造动作。不能把以上类别写成固定优先级循环。

## 现有接口的缺口

`unit tasks` 是资源和地形映射的候选建议，扫描范围有限，不含完整水域／特色改良集合，也没有路径、安全或跨建造者争用判断。它的几何最近单位不是原生最快可达单位；扫描时的城市名不是地块实际工作城市。见 `src/civ_mcp/lua/units.py` 的 `get_builder_tasks` 与 `src/civ_mcp/narrate.py` 的任务展示。

当前位置的 `valid_improvements` 列出原生接受的改良，但逐项原生检查失败可能被跳过，不能把空列表解释为全部明确不合法。远处的候选尤其不能冒充已通过当前位置原生检查。地图地块产出也不能替代 `city workforce` 的实际工作与城市边际收益。

独立审查建议的最小输入为：世界／玩家／回合及来源回执、单个单位当前状态、主模型给定局部目标、预留任务和少量带 unknown 的候选。Jev 返回候选 ID 或要求补充事实；Choice 本身不生成解释，事实来源应由候选元数据保留。不能伪造模型生成的推理说明。

后续若接入执行，主模型仍持有唯一 CLI 所有权；每次执行前重新检查未决门禁、身份、回合和同回合状态变化，重新检查跨单位占用，原生执行时复核资格。`--dry-run` 仅静态校验，不能证明原生合法性。高置信度也不能解除 pending 或证明下一回合安全。

## 已完成的 Jev 实验

已通过本机环境变量 `TYPESAFE_API_KEY` 成功连接官方接口。密钥只在请求头内存中使用，没有写入脚本、报告或日志。固定使用 `jev-1.14.0`；实际响应确认该模型 ID。

测试集在调用前写入固定脚本，共 8 个场景：重建矿山、最后一次数改良鱼资源、免费修复、区域预留与伐木、特色改良与连接硝石、远程安全证据不足、两名建造者争用任务、不可逆收获取舍。前两个由历史实机事实人工压缩；鱼资源资格由历史成功动作追认。其余为受控夹具，不是本轮原生资格或游戏效果验收。

先分别发送 8 个单题请求，再将同一组 8 题合并发送 3 次，后两次改变候选排列顺序。合并的题目相互独立，不能看见其他题的回答。所有请求只做固定夹具判断，脚本没有游戏连接、命令分发或推进循环。

| 实测指标 | 结果 |
| --- | --- |
| POST 请求 | 11 次，全部 HTTP 200、结构校验通过 |
| 单题延迟 | 0.672–0.727 秒，中位 0.706752 秒 |
| 8 题串行 API 延迟合计 | 5.642553 秒 |
| 8 题合并延迟，三次 | 0.710833／0.737616／0.668144 秒 |
| 合并首轮与单题串行合计之比 | 约 7.94 倍，仅此固定 API 调用组织比较 |
| 人工参考选择匹配 | 32／32 次判断，实际只有 8 个独立场景 |
| 输入／输出 token | 13730／1473，以接口 usage 为准 |

这完成了固定夹具的指令遵循与接口冒烟验证，且本小样本合并提问能显著降低网络串行成本。延迟包含客户端请求往返、响应解析与校验，不包含候选构造、输入准备、主模型复核、CLI 查询和执行确认。它不是 Jev 对主模型推理速度的比较，也不是 32 个独立真实回合的准确率，更不是整局倍率。

场景目标和候选由主模型编写，几个错误选项明显不合适，形成较容易的任务；例如题面直接要求重建矿山，或明确说明另一单位已占用任务。参考选择也是主模型预先写定，并非独立专家或游戏结果标签。后两轮仅改变候选字典的排列，没有重映射答案标签或打乱题序。重复输入、调用顺序、合并后共享更多上下文及可能的服务缓存均未被隔离；没有校准置信度阈值，没有验证中文输入、生产级超时／错误恢复、复杂城市规划或战争预测。Jev 的高置信度不等于正确率或执行授权。

合并请求共用包含八个场景的 state；本轮没有验证服务端上下文隔离，也没有运行八个客户端并发请求。已告知的任务争用题不代表模型能够发现多个新建议之间的冲突。世界切换、未决请求、同回合中间动作及资格过期也尚未进入夹具。独立审查复核了 11 份请求哈希、原始响应及汇总数字，确认参考字段未发送，但该审查不能把手写参考转换为独立策略质量标签。

## 下一步建议

先补真实建造者候选的信息质量，再扩大影子实验。主模型提供城市目标和任务分配，Jev 一次比较多个相互独立单位的局部候选；任何依赖前一动作结果的选择返回模型重新判断。候选不足、争用、危险路径、收获及战略冲突继续升级处理。

下一轮应预先登记未参与提示设计的真实历史场景与困难反例，覆盖到达后移动力不足、空列表读取失败、同回合陈旧、区域预留、远程资格未知和未决请求。分别记录参考意见、Jev 建议、主模型修改、增加的查询、API／思考／执行墙钟和最终动作结果。先验证少量影子回合对总决策时间的净收益及质量，再考虑让 Jev 建议进入受控执行；不直接换成通用自动对局脚本。
