# 终局占城的原请求确认

**Status:** ready-for-agent

**Approval:** 2026-10-27 用户确认公开领域入口＋实体查询的隔离测试边界，以及 01→02 两任务依赖；现场只读，旧 owner 与 pending 保留。

## Problem Statement

T237 的最后一次近战占领已令游戏引擎判定苏美尔征服胜利，但 CLI 仍返回 `OUTCOME_UNKNOWN / CAPTURE_POSITION_UNCONFIRMED` 并保留未决动作。目标原首都已归本方；攻击驱逐舰停在相邻海格，未满足普通占领要求的进城位置。模型只能把已经获胜的现场与仍未完成的请求分别报告，不能安全地结束原动作生命周期。

用户要求修复并验证这个确认问题，同时保留现有终局、全部存档、原始证据和原动作所有权，不重复攻击，不通过重启、读档、注入或清门禁制造成功。

## Solution

为原请求增加严格受限的终局占领确认规则：原世界／回合／玩家、动作 token、精确战斗参与者、原目标城市归本方和本方原生征服胜利同时成立时，允许攻击单位仍在目标相邻格的终局完成状态。普通非终局占领仍等待攻击者真正进城，未知或冲突证据继续保留未决。

沿用现有命名 CLI 和 ActionLifecycle，通过实体查询只读确认既有动作，不要求模型再次输入攻击命令，不新增提交路径或后台任务。修复版在隔离的真实领域入口与 Lua 执行夹具验证。当前旧进程及其冻结的确认代码保持不变；实机只读复核原生胜利和未决归属，不能将离线通过表述为旧 owner 已应用补丁。

## User Stories

1. As a CLI 游戏操作者, I want 最后一次占领触发征服胜利后原请求能得到有据的完成结果, so that 已完成游戏不会继续被错误的未决门禁挡住。
2. As a CLI 游戏操作者, I want 通过单位或城市查询确认旧请求, so that 无需再次输入外观为攻击的命令。
3. As a CLI 游戏操作者, I want 确认过程不提交任何攻击或移动操作, so that 现有终局不会发生额外变更。
4. As a CLI 游戏操作者, I want 同一次请求始终只提交一次原生操作, so that 丢回应或迟到终局不会导致重复攻击。
5. As a Runtime 维护者, I want 终局确认绑定原 token 和精确攻击者、城市中心组件, so that 其他战斗不能为原请求补签。
6. As a Runtime 维护者, I want 确认原世界、回合和本地玩家仍匹配, so that 其他对局或回合的胜利不能确认旧请求。
7. As a Runtime 维护者, I want 已观察到的身份冲突继续锁存, so that 返回旧身份也不能错误地释放门禁。
8. As a Runtime 维护者, I want 本方获胜依据原生获胜队伍和玩家队伍而非展示名称, so that 队伍 ID 与玩家 ID 不同也能正确判断。
9. As a Runtime 维护者, I want 只有原生征服胜利满足本次终局例外, so that 科技、文化、宗教、外交胜利及未知类型不会放松占领确认。
10. As a Runtime 维护者, I want 敌方胜利或目标未归本方时继续保持未决, so that 胜利画面本身不能成为通用清门禁信号。
11. As a Runtime 维护者, I want 缺少完整战斗见证或原生 API 不可用时继续保持未决, so that 事实缺失不会被当成成功。
12. As a Runtime 维护者, I want 非终局占领仍要求攻击者实际进城, so that 原有异步占领安全条件不退化。
13. As a Runtime 维护者, I want 非相邻、被替换或无法识别的攻击者不能走终局例外, so that 无关位置变化不能确认占领。
14. As a Runtime 维护者, I want 确认成功只退役原请求及其监听器, so that 不影响其他生命周期或伪造后续动作资格。
15. As a 测试维护者, I want 用 T237 实际症状形成先红后绿的隔离回归, so that 修复针对本次缺陷而非仅检查文案。
16. As a 测试维护者, I want 同时验证成功、证据迟到和证据缺失, so that 确认过程既能完成也能安全等待。
17. As a 测试维护者, I want 在公开领域入口核对 pending 与原生提交计数, so that 内部实现调整不会令测试失去用户语义。
18. As a 对局所有者, I want 原终局、检查点和旧证据不被覆盖或删除, so that 现有胜利仍可审计和复现。
19. As a 对局所有者, I want 清楚区分修复版离线验证与旧会话现场复核, so that 不会把另一个空会话误当原动作已确认。
20. As a 项目维护者, I want 规格、任务依赖、提交和验收结果相互关联, so that 后续能追溯修复范围与尚存限制。

## Implementation Decisions

- 保留动作生命周期的单一所有者；确认沿原请求保存的查询和战斗见证执行，不从普通概览缓存追认。
- 攻城确认器负责终局占领的领域证据，不在 CLI 层添加清 pending 的特殊分支。
- 终局例外必须保留现有进入／返回、精确 CombatVisEnd、攻击者完整身份、目标坐标与城市归属变化等约束；只放宽终局时的最终进城位置，且攻击者仍须与目标相邻。
- 原生获胜队伍必须与本地玩家的原生队伍匹配，胜利选择器必须解析为征服胜利；不比较显示名称，不把队伍 ID 当成玩家 ID。
- 对原生结果、身份或组件的有效冲突继续锁存；字段缺失、API 异常、未知胜利类型和证据不完整保持结果未知。
- 保留普通伤害、攻击者死亡和正常进城的确认路径；只有终局例外不能扩展为一般的城市归属变化即完成。
- 确认输出需可区分普通进城完成和终局占领完成，不能声称驱逐舰已经进入城市；具体格式沿当前结果协议最小扩展。
- 使用现有单位／城市查询发起非等待式只读确认，确认成功后只清原动作，不提交任何新操作。
- 原 CLI owner 保留。现有进程没有安全热加载能力，已保存的确认查询也已冻结；本任务不增加热加载、跨进程接管或任意代码入口。
- 工作使用单一集成分支，各实施任务使用独立 worktree，完成后由合并子代理汇入集成分支；不 push，不改写历史。
- 本地 Markdown tracker 已由项目开发指南确认，规格和逐任务文件存放在该 tracker；完成后在所属对局追加可提交的修复与验收记录。

## Testing Decisions

- 主要测试边界为公开 GameState 的攻击入口与单位／城市查询，内部执行真实生成的 Lua 和真实 ActionLifecycle；复用现有攻城、动作确认及身份门禁测试夹具，不新建绕过生产逻辑的确认模型。
- 测试从固定输入和原生事件观察最终结果、未决门禁、监听器归属及原生操作次数；不以源码字符串或私有标记值替代行为断言。
- 第一个回归重现海军近战、城市归属改变、精确战斗见证、本方征服胜利、攻击者留在相邻海格，并先运行得到与 T237 相同的未决症状，再实现最小修复。
- 延后终局证据的场景必须先保持未决，再通过实体查询完成，原生操作计数始终为一；查询后实际零新增攻击、移动、保存或换档。
- 覆盖非终局、敌方胜利、其他胜利类型、未知类型、缺少精确战斗事件、目标未归本方、单位身份变化、单位非相邻、原世界／回合／玩家变化及已锁存冲突等反例。
- 补充命名 CLI 实体查询的确认与结果展示验收；仅在既有测试边界无法覆盖时增加最小协议测试，不为本任务新增通用 CLI 或 mock 专用接口。
- 受影响的攻城、动作确认、未决调度、终局边界及 CLI 定向测试通过后停止扩大范围；必要时做编译检查和 diff 检查。
- 现场仅复用原 CLI 会话读取 pending 与原生终局；不启动第二个游戏客户端、不故障注入、不加载存档、不再次攻击，不宣称修复版已在旧 owner 中实机执行。

## Out of Scope

- 重玩或回档最后一次攻击，修改终局、城市、单位或原生监听记录。
- 手工清门禁、强制取消旧请求、重启原 owner、热加载或跨进程迁移 pending。
- 新增通用 pending 清理／接管命令，或任意 Python／Lua 操作入口。
- 修复间谍返程确认、其他游戏策略、其他胜利路线或重构整个 Runtime。
- 将已获胜作为任意未决动作的统一完成依据。
- 对外发布、push、创建远端 issue 或 PR。
