## 政策：在任何副作用前拒绝不完整方案

旧实现虽然构造全部最终槽位，却允许最终仍有空槽。T10 首次只提交军事槽会消耗免费换卡机会，经济空槽又阻止推进。原版 `GovernmentScreen.lua` 在任何槽为空时禁用确认按钮；本地调用绕过了这一保护。

`lua/policies.py` 在付款或提交前检查所有最终槽位。变更方案仍有空槽时返回 `POLICY_PLAN_INCOMPLETE` 和槽位编号，不自动选卡；省略槽位仍保留原卡，完全不变的旧空槽方案仍可零提交确认。`NONE` 不能使变更后的最终方案留下空槽。

离线红灯：`pytest -q tests/test_policy_lua_execution.py -k partial_first_policy` 在旧实现实际返回 `POLICIES_SET` 时失败。修复后验证部分方案不改变槽位、不付款、不请求换卡、不留下 pending，随后完整方案仍可单次提交。正常换卡夹具改为完整政府槽位，原来允许留下空槽的用例改为提交前拒绝用例；延迟、付费、丢回应、范围变化与完整方案回读继续覆盖。

实机：从本轮已确认 `cli100_1424_t10` 加载。`policy set 0=POLICY_DISCIPLINE` 被明确拒绝；两槽仍为空、金币仍 51、无 pending。随后在同一 T10 提交 `0=POLICY_DISCIPLINE 1=POLICY_URBAN_PLANNING`，原生确认 `POLICIES_SET`。处理市政待办后确认 T10→T11，无需恢复或重复换卡。

## 使者：分开 UI 提交见证与 GameCore 权威计数

旧实现的完成判定只读 InGame 计数。T101 从原检查点复现非斯同类故障时，UI 请求返回 true，但 InGame 一直显示令牌 1、非斯使者 3；独立 GameCore 回读实际为令牌 0、使者 4。这是成功动作被缓存旧值阻止确认，不能通过重复派遣解决。

修复保留原动作所有者和单次提交：

- 提交前在 GameCore 冻结原 token、世界／回合／玩家、目标身份与双侧计数；无法取得有效基线时明确零请求拒绝。
- InGame 仅提交一次，并保留精确请求进入／返回见证；资格方法属于 UI，继续在 InGame 核验。
- 确认同时要求匹配的 InGame 原见证、GameCore 原基线，以及令牌恰少一枚、指定城邦使者增加。没有用单侧变化、成功文案或缓存刷新替代确认。
- GameCore 观测到范围改变后锁存失效；恢复旧字段不能追认。查询不能退役 pending。
- `city-state list` 从 GameCore 读取计数和宗主信息，结合 UI 独有资格及读取前后的本地范围，避免把已花掉的令牌继续显示为可用。

离线红灯：新增 UI 计数持续旧值的真实 Lua 回归，在修复前返回 `OUTCOME_UNKNOWN`。修复后只提交一次，仍能由 GameCore 双侧差分确认。补充权威列表、旧 UI 令牌不能授权额外派遣、缺失／错 token 引擎记录、Core 范围失效锁存、准备读取失败和纯查询不退役请求的回归。测试 adapter 将 UI 独有资格 API 限制在 InGame，防止错误跨上下文调用。

实机：从原 `cli100_1424_t101` 再测 `city-state envoy 9`。修复版单次返回 `ENVOY_SENT|player:9|remaining:0|envoys:3->4`；列表读到 0 枚可用令牌、非斯 4 使者且我方为宗主；pending 全部 false。关闭新发现自然奇观弹窗后确认 T101→T102，保存 `cli100_1424_fixed_t102`。政策复测完成后，已恢复此 T102 并再次通过 `verify state`。
